Sean summarized the previous update as a proposal for agent identity based on W3C Decentralized Identifiers (DIDs). The proposal includes a Web-based DID method for agents, use of DID-based identity for discovery and authentication, integration with existing `did:web` deployments where possible, and discovery-service support so that agents can find other agents or services they need.

Song noted that the protocol draft also needs to reflect the group's planned openness to OAuth and OIDC integration. Sean clarified that the identity work covers both agent-to-agent and agent-to-resource scenarios:

- For **agent-to-agent** communication, the group has discussed a DID-based identity and authentication approach for agents.
- For **agent-to-resource** access, the proposal includes a DID/OIDC identity-provider path in which DID authentication can be converted into an OIDC-style ID token. The agent can then use the token in an OAuth flow to obtain access to protected resources.

### IV. Proposed Model for Agent Understanding of Network State and Permissions

Sean presented a proposal described as an open verifiable agent identity / agent-network model for the Agent Web. Song introduced the topic by noting that it is not a completely new subject for the CG. Questions about the model behind the Agent Web have come up across several earlier meetings, but participants have also advised that the current use-case and protocol documents should be finalized without adding large new feature areas. Song therefore framed Sean's presentation as a possible extension or explanatory model related to existing white-paper and protocol sections, rather than as a request to expand the immediate publication scope.

Sean explained the motivation as a gap between two sides of agent interoperability:

- Many current and emerging standards try to make the network able to accept agents, for example by adapting identity, credentials, OAuth, and OIDC flows so agents can authenticate and obtain tokens.
- Less work has addressed how agents themselves should understand the network once they encounter identity, authentication, authorization, relationship, or permission problems.

Sean argued that prompts alone are not a reliable solution for this problem. Different agents and vendors may encode network-handling instructions differently, and prompt-based behavior is not structured enough for a high-frequency function such as network access. Instead, agents should have a shared contract for understanding network state and permission feedback.

The proposed loop has four broad steps:

1. An agent asks its runtime for the current network state, including the agent identity, relationships, credentials, and relevant permission context.
2. The agent interprets the structured state and chooses an action, such as sending a message, requesting authentication, requesting authorization, or finding an approval service.
3. The runtime maps the agent's structured action to the appropriate network protocol or function call.
4. The network returns structured feedback or status, which the runtime maps back into agent-understandable state so the agent can update its plan and take the next step.

Sean said the goal is not to replace IAM systems, OAuth, PEP/PDP components, or other authorization infrastructure. Instead, the model would standardize how their outputs are exposed to agents in a richer and more semantic form, so agents can understand what went wrong and what they should do next.

### V. Agent-to-Agent and Agent-to-Resource Permission Flows

Sean described two basic flows where structured state and permission feedback are useful.

For **agent-to-agent** interaction, Agent A may try to contact Agent B using an identity such as a DID or an ANP-related identity. If Agent A lacks permission to send the message, Agent B or the receiving runtime should return a structured challenge or authorization hint. Agent A can then interpret the hint, discover or load an approval skill, request user approval if needed, obtain a grant, ticket, or similar credential, and retry the request.

For **agent-to-resource** interaction, an agent may try to access a protected resource and receive an authorization or permission error. Instead of returning only an ordinary error code, the resource side or IAM layer could provide structured information about what approval process, token, ticket, or credential is required. The agent can then follow an approval flow, obtain the needed authorization material, and retry access.

Sean emphasized that these flows are especially important for agents delegated to act independently. When there is no human directly operating the agent at each step, the agent needs interoperable ways to understand permission problems and decide whether to request approval, obtain credentials, or stop.

### VI. Message-Based and Intent-Based Authorization

Sean also highlighted a separate authorization problem in agent-to-agent messaging. Even after one agent has permission to contact another, the receiving agent may need to analyze the **intent** contained in each message. The same API endpoint or message interface can carry different requests with different authorization implications.

Sean noted that traditional OAuth-style authorization often focuses on access to a URI, API, or resource scope. In agent messaging, however, the permission decision may depend on the specific intent expressed in the message. Some intents may be safe, while others may require a stronger credential, additional user approval, or a different authorization policy.

The group therefore discussed the need to explore permission control for message-based interactions, including how an agent can represent requested intent and how the receiving side can return structured authorization recommendations.

### VII. Possible Standardization Targets and ANP Testbed

Sean suggested several possible areas for standardization:

- A standard structured representation of interaction or network state, likely in JSON.
- A standard structured representation of agent actions or commands that can be passed to a runtime.
- A standard structured authorization recommendation or challenge format returned to agents.
- A permission-control flow for agent-to-agent message interactions, especially where authorization depends on message intent.

Sean said ANP could serve as a practical runtime or testbed for these ideas. ANP already has related DID-based identity and authentication work, agent-to-agent messaging capabilities, and proposed DID/identity-provider components. These could be used to test agent-to-agent authorization, agent-to-resource authorization, and message-based authorization scenarios.

Song asked how the presentation maps to the current documents. He suggested that the ideas correspond most closely to existing discussion in the white paper around key issues the agent protocol aims to solve, and to the protocol draft's section on cross-platform identity authentication over HTTP. Sean agreed with this mapping.

Song reiterated that the CG should focus its limited resources on finalizing the current documents, and should treat this model as an explanatory extension or future direction rather than a large new feature area for the immediate draft.
