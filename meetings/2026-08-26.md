### II. Pull Request #45: Separating Agent Identity from DID Method Trust Models

Sean presented the open pull request and the accompanying 10-minute talk. The change is an architectural split, not a formatting cleanup. Common agent authentication is made reusable, while each DID method keeps its own trust and lifecycle rules.

The pull request was opened on August 26, 2026 by Gaowei Chang. It changes five files and adds three companion specifications:

| File | Role | Question answered |
| --- | --- | --- |
| `agent-identity.html` | Common protocol | How an agent proves control of a DID key over HTTP |
| `did-method-profiles.html` | Binding layer | How each DID method is resolved and validated |
| `did-wba.html` | Method specification | How `did:wba` is created, resolved, updated, and deactivated |
| `protocol.html` | Index and migration | Where existing readers and fragment links are redirected |
| `tests/test_identity_documents.py` | Structural tests | What document integrity and compatibility anchors are checked |

Before the split, `protocol.html` mixed the agent identity model, HTTP authentication, the `did:wba` lifecycle, and `did:web` / `did:webvh` compatibility in one section. After the split:

- `agent-identity.html` holds DID-method-agnostic HTTP authentication (RFC 9421, RFC 9530, `keyid` as a complete DID URL, replay protection, access tokens, and the distinction between authentication and authorization).
- `did-method-profiles.html` holds binding profiles for `did:wba`, native `did:web`, and `did:webvh`.
- `did-wba.html` holds the standalone `did:wba` DID Method Specification (identifier syntax, `e1_` path binding, CRUD, and Data Integrity proof). HTTP signature and access-token flows now live in `agent-identity.html`.
- `protocol.html` keeps `#agent-identity` as an index with migration anchors so existing fragments continue to resolve.

Agent Description, Agent Discovery, and the other protocol sections are unchanged.

The kernel of the design, as presented, is:

- Identity proof is common.
- Trust validation is pluggable.
- The server selects the trust rules from the DID itself.
- The DID method name is authoritative.
- A failed resolution is not retried under another method.

Sean described the common authentication flow as:

1. The agent client signs the HTTP method, URI, digest, time, and nonce.
2. The verifier reads `keyid` and selects one Binding Profile.
3. The resolver returns a validated DID Document or a failure.
4. The verifier then checks the DID-key relation, signature, digest, replay window, and authorization.

A 401 response remains an authentication failure. A 403 response means the caller authenticated but is not permitted.

### III. Three Binding Profiles and Distinct Trust Models

One authentication flow is intended to support three distinct trust models. Shared protocol does not mean shared security assumptions.

- **`did:wba`** is trusted by DNS, HTTPS, and Web PKI. The profile validates HTTPS resolution and, when applicable, the `e1_` thumbprint and Data Integrity proof.
- **Native `did:web`** is also trusted by DNS, HTTPS, and Web PKI, but it follows native `did:web` resolution and does not require `did:wba`-specific fingerprint or proof rules.
- **`did:webvh`** is trusted by its self-certifying identifier (SCID) and verifiable history. The profile validates the hash-linked update log, authorization, version, and deactivation state.

Sean restated the deployment intuition from earlier meetings. Native `did:web` may suit organizations that already operate a public website. Those deployments can later move to `did:webvh` if they need verifiable history. End users who do not operate a website may host DID Documents with `did:wba` or `did:webvh`. `did:wba` remains a standalone DID method; it is not a replacement for `did:web`.

Method fallback is prohibited. A failed `did:web` resolution must not be retried as `did:wba` or `did:webvh`. The stated reason is to avoid applying the wrong trust assumptions and creating method-confusion or downgrade vulnerabilities.

### IV. `did:wba` Lifecycle, Tokens, and Relationship to OAuth

In the standalone `did:wba` method, the `e1_` profile places an Ed25519 key thumbprint in the path. The verifier recomputes the RFC 7638 thumbprint, and the DID Document proof binds the document to that key. Changing the binding key therefore changes the path DID, because the public-key fingerprint is part of the identifier. Stable user-facing naming belongs above the DID method.

Legacy path DIDs without a fingerprint can still be parsed, but the recommended form is the fingerprint-bound identifier. Sean said the exact legacy syntax and validation profile should be clarified in review.

On authentication versus authorization, the presentation was explicit:

- An authenticated DID does not automatically receive access. Authentication proves control of an authorized DID key. Authorization remains a separate server decision.
- An access token issued after DID authentication is an optimization that avoids repeating DID resolution and signature verification. It does not replace the initial proof.
- This pull request defines DID-based HTTP authentication, not a complete delegation framework. OAuth can be layered on top; that integration is outside PR #45.

### V. Open Review Questions from the Talk

Sean asked the group to treat the document architecture as the first decision, then track remaining interoperability details as follow-up work unless the group wants implementation-ready closure before merge:

1. Are the three specification boundaries clear (common protocol, binding profiles, `did:wba` method)?
2. Is method selection from the DID string, with no fallback, sufficiently explicit and acceptable?
3. What is the minimum interoperable cryptographic set (algorithms, digest requirements, and test vectors)?
4. Is replay protection fully closed (nonce requirements, unique request identifiers, and cache behavior)?

The current tests check document structure: balanced section tags, unique HTML IDs, resolvable local links, migration anchors, and complete ReSpec documents. They do not yet cover ReSpec browser rendering, HTTP signature test vectors, profile success and failure cases, or replay and method-confusion tests.

Sean’s preferred near-term outcome is to accept the document architecture. Minimum algorithms, replay uniqueness, anti-rollback behavior, and executable test vectors can be tracked as explicit follow-up, or resolved before merge if the group wants implementation readiness now.

When Song asked about the next meeting, Sean proposed continuing the protocol-structure discussion. Before this split, the draft had one DID method and no clear place to add other authentication mechanisms. The new structure is intended to make later support for additional methods, including OAuth client metadata discussed in the previous meeting, easier to specify without mixing trust models.

### VI. 3GPP CT WG3 Update

Song reported that 3GPP CT WG3, which specifies core-network and terminal protocols for 5G and 6G, was meeting during the same week. Members of this Community Group and of the ANP open-source community had been invited to contribute to proposals there. An open discussion in CT3 was scheduled for August 26. Song said he would provide more detailed feedback by the end of the week.

He placed the update in this CG because the telecom community has shown growing interest in Internet-based decentralized identity. CG participants have already been invited to unofficial 3GPP discussions, and 3GPP experts have seen value in the identity encapsulation used by agent protocols.

In this week’s CT3 material, Song highlighted an Agentic Network proposal for 3GPP 6G based on DID. According to the discussion he summarized:

- Internet-based decentralized identity is expected to disrupt traditional telecom identity management, which some experts see as an opportunity for an agent-centric 6G network.
- W3C DID, which has been specified for several years, is viewed as stable and flexible enough to be one optional identity approach for future 6G specifications.
- Other options remain under discussion, including OAuth and a proposal Song referred to as AIP (he was not certain of the expansion during the call; the CT3 study item itself is recorded as FS_6G_AIP_CT, “Study on the Protocol for AI in 6G”).

Song emphasized that these 3GPP discussions are still open.

### VII. *3GPP Highlights* Issue 12 and the Description of ANP

Song also shared a recent 3GPP newsletter, *3GPP Highlights* Issue 12 (June 2026), and said it would be attached to the meeting minutes. The relevant article is “AI and Agentic Protocols for 6G”, by Abdessamad El Moatamid (Huawei, 3GPP CT WG3), Zhenning Huang (China Mobile, 3GPP CT WG3), and Xuefei Zhang (Huawei, 3GPP CT WG3).

The article argues that as agentic AI matures in the Web and IT world, several open-source agent protocols have appeared, while 3GPP, IETF, and other SDOs are working toward a standardized set of agentic/AI protocols. It says the 3GPP CT WG3 study on the protocol for AI in 6G (FS_6G_AIP_CT) is expected to evaluate the available protocols.

Among the “leading AI protocols”, the newsletter lists Agent2Agent (A2A) and then describes ANP as follows:

> The Agent Network Protocol (ANP) is also an open-source protocol introduced at the W3C WebAgents CG conference in February 2025. It focuses on enabling the communication between AI Agents with the ambition to build an open, secure and efficient collaborative network to connect and enable secure collaboration between billions of AI Agents from different companies and organizations.

The newsletter then states that ANP has a three-layer architecture:

- **Identity and Secure Communication Layer**, designed for authentication and encrypted communications between AI Agents.
- **Meta-Protocol Layer**, defining how AI Agents dynamically negotiate communication protocols.
- **Application Protocol Layer**, including AI Agent description and discovery.

The article points readers to https://agent-network-protocol.com/.

That description is directly relevant to this Community Group. The identity and secure-communication layer is the same area covered by PR #45: DID-based agent identity, HTTP authentication, and encrypted communication. The application-protocol layer corresponds to the Agent Description and Agent Discovery work already in the CG protocol draft. Song noted that the newsletter presents ANP as coordination between the open-source community and W3C, and that it also summarizes related work in IETF and other SDOs.

The same article places ANP beside other open-source protocols and SDO activity:

- **A2A**, published by Google in April 2025 and later donated to the Linux Foundation, using an Agent Card to advertise identity, capabilities, and interaction requirements.
- **MCP**, released by Anthropic in November 2024, focused on connecting models or agents to tools, resources, and databases.
- **IETF**, with AI-protocol discussion since IETF 123 (July 2025) and the CATALIST BoF at IETF 125 (18 March 2026) as a coordination forum.
- **ETSI**, including ISG ENI work on AI agents for network slicing, mobile core networks, multi-agent frameworks, and agent interfaces.

On the 3GPP side, the article reviews Rel-20 6G study progress and says stage 3 agentic/AI-enabled protocols will need to cover at least:

- Communications between AI Agents on UEs via the 6G network
- Communications between AI Agents on UEs and the 6G network
- Communications between Network AI Agents within the 6G Core Network
- Communications between 3rd Party AI Agents and the 6G network
- AI training/inferencing capabilities

The requirements it draws from stage 2 work, open-source protocols, and IETF activity include AI Agent identity management; security, authentication, and authorization; dynamic networking for capability registration and discovery; and intent processing. It then asks whether 3GPP should rely on protocols defined elsewhere, define a custom 3GPP set, or use a combination of existing open-source protocols.

Song said the newsletter is useful context for anyone following agent protocols in the telecom industry, and that he would include it after the call.

### VIII. Reference Implementation Question and CAIP-10 Comment

A chat question asked where the code for the DID method is. Song and Sean pointed to the ANP GitHub repository, which includes the `did:wba` reference implementation. Demonstration material from earlier meetings is also linked from previous minutes.

Ren Yushan then shared a comparison between ANP identity and blockchain identity. He pointed to CAIP-10, under which each blockchain can expose an account identifier with DID-like properties. In his view, the common elements are an identifier plus a public/private key pair; the main difference is that a blockchain records accounts on-chain, whereas ANP currently depends on hosted DID Documents. He suggested this as a possible route for unifying DID methods.

Sean said the current design reuses Web infrastructure, and that a common model for blockchain-backed DIDs is worth further study. He connected the comment to the adapter approach already under discussion: a shared identity model, with method-specific adapters for resolution and validation. Song welcomed Ren to the call and thanked him for the input.
