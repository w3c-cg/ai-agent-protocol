## Discussion Topics

### I. Multiple DID Methods for Agent Identity

Sean presented a proposal for the Agent Network Protocol to support multiple DID methods rather than requiring a single identity mechanism. The methods discussed were:

- **`did:web`**, for deployments that want to use the established Web and domain-name infrastructure.
- **`did:wba`**, the Web-based agent DID method currently defined by the CG protocol draft, which extends `did:web` with agent-oriented interoperability and additional cryptographic-binding and authentication rules.
- **`did:webvh`**, for deployments that require verifiable history and stronger support for tracking DID document changes.

Sean explained that the methods address different deployment, compatibility, and security requirements. The broader aim is to allow agents using different identity systems to participate in a common communication environment without requiring every implementation to adopt the same DID method.

The current CG protocol draft defines `did:wba` as its core Web-based DID method and also documents a compatibility mode for native `did:web`. Support for additional methods, including `did:webvh`, was discussed as part of the broader proposal rather than as an already completed part of the current draft.

### II. Multi-Device Identity and Endpoint Management

Sean discussed the challenge of enabling one user to access and manage agents from multiple devices. A single identity may need to be usable from a phone, computer, or other client while each device retains its own security boundary.

The proposed approach uses device-specific keys and access controls associated with the user's identity and service configuration. This lets an authorized device participate without requiring all devices to share the same private key. Devices can be added, managed, or removed according to implementation policy, while the DID document or related identity metadata provides a stable basis for resolving the identity and its current service information.

Sean clarified later in the discussion that this multi-device design is primarily intended for human users operating agents from multiple devices. It should not be interpreted as requiring an autonomous agent to register itself again whenever it runs on another device or execution environment.

### III. Agent Client and End-to-End Encrypted Communication

Sean demonstrated an agent client used to manage agents and communicate across devices and networks. The demonstration showed agents exchanging messages through an end-to-end encrypted channel.

The design keeps message contents confidential between the participating endpoints, including when a relay or other intermediary is needed to route messages. Identity resolution supplies the keys and service information needed to establish communication, while local device-key management and access-control decisions determine which clients can act for the user or agent.

The demonstration illustrated how identity, endpoint resolution, device authorization, and encrypted messaging fit together as parts of a larger agent communication system.

### IV. Higher-Level Identifier and Metadata Requirements

George suggested that the CG consider defining the protocol at a semantic level above any one identifier technology. Instead of treating a DID as the only possible identity primitive, the specification could define what an identifier must resolve to and which metadata, keys, endpoints, and verification properties an implementation needs.

George compared this approach to systems in which an identifier is associated with standardized client metadata. Under such a model, DIDs would remain important supported mechanisms, but the protocol could also accommodate non-DID identity and resolution systems that satisfy the same requirements.

Sean agreed that this abstraction was worth exploring. He noted that ANP aims to support different identity systems while preserving consistent mechanisms for authentication and end-to-end encryption. The group identified the intrinsic or technology-independent requirements of an identity system as a topic for further mailing-list or GitHub discussion.

### V. Agent-Native Identity and Registration

Ren asked how agent-native identities would be established and whether an agent would have to repeat registration across devices. He also asked how the registration process relates to agents that operate independently of a particular human-facing client.

Sean said implementations can support different registration and account-establishment methods, including email- or mobile-phone-based registration where appropriate. These methods are implementation choices rather than a single registration mechanism mandated for every agent identity.

Sean reiterated that the multi-device flow presented in the meeting addresses a human user's access to agents. Agent-native identity and lifecycle requirements are related but distinct and should be documented separately so that user-device enrollment is not conflated with agent registration or identity creation.

### VI. Community Group Document Follow-Up

Roy asked whether the discussion required updates to the agent-identity section of the Community Group documents. Sean said that the relevant document had not yet been modified and agreed to check with Gaowei about whether the section should be updated to reflect the meeting's conclusions.

Participants were invited to continue the discussion through the public mailing list and the CG GitHub repository. In particular, the group should further define the common requirements that an identity and resolution system must satisfy, and determine how those requirements relate to the DID methods and compatibility mechanisms already described in the protocol draft.
