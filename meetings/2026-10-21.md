### III. Agent Authorization proposal: identity, claims, and permission

Gaowei presented the [Agent Authorization slides](materials/2026-10-21/w3c-Agent-Authorization-Proposal.pptx) and introduced [PR #46: Add Agent Authorization specification](https://github.com/w3c-cg/ai-agent-protocol/pull/46). He said the PR had been submitted but not merged and asked for feedback on the overall design before refining the details.

The proposal addresses two related questions:

1. How can an agent demonstrate an attribute, organizational role, or mandate to act for a person or organization?
2. How does the agent obtain permission to access a resource or perform an operation?

The proposed division of responsibilities is:

- **DID and authentication proofs** establish the agent's identifier and control of an authorized key. They do not by themselves establish an organizational role, user consent, or resource permission.
- **Verifiable Credentials (VCs)** can carry signed claims about roles or direct mandates. A verifier still needs to assess issuer authority, holder binding, credential status, constraints, and local policy.
- **OAuth** manages resource-side grants, scopes, access tokens, refresh, and revocation. The authorization server and resource server make and enforce access decisions independently of identity discovery.

The shared material does not define automatic VC-to-OAuth token conversion. PR #46's detailed VC Profile is reserved in the contributed snapshot, so the intended VC architecture should not be read as a completed, implementable conformance profile.

### IV. Two approaches to DID and OAuth client onboarding

Gaowei outlined two approaches and explicitly said he had not yet decided which was preferable.

**Approach A: DID-native client identity.** Use the agent DID as the OAuth `client_id`. A validated DID Document identifies authorized authentication keys and links to self-published, CIMD-style client metadata. The shared slides describe binding the metadata URL to a SHA-256 digest of its exact bytes. The authorization server validates the DID and metadata binding, applies client-admission policy, and verifies a fresh `private_key_jwt` at the token endpoint before independently checking the grant. OAuth continues to handle consent, grants, and tokens.

This borrows the self-published metadata idea from **Client ID Metadata Documents (CIMD)**, but it is a distinct DID-native profile: standard CIMD uses an HTTPS metadata-document URL, rather than a DID, as `client_id`. PR #46 currently specifies the DID-native approach.

**Approach B: retain CIMD's HTTPS client identifier and add DID binding.** Keep the HTTPS metadata URL as `client_id` and the normal CIMD/OAuth path, while adding a verifiable association with a DID. The supplemental slides illustrate an `agent_did` extension, a DID Document back-reference to the client URL, and a cryptographic key binding. A server that validates the extension can rely on the verified DID as identity evidence. A server performing only ordinary CIMD checks has not thereby validated a DID.

The second approach remains an alternative for discussion, not a second normative path already implemented in PR #46. Its wire format, binding proofs, freshness, key rotation, migration, and revocation still need specification. Cross-references alone do not establish a secure binding, and neither approach grants resource access merely because metadata or identity validation succeeds.

Chris clarified that the component called a “CIMD server” is essentially Web publication of metadata, rather than a separate authorization protocol. Gaowei agreed and emphasized the value of discovering public-key information and reusing OAuth instead of inventing a new authorization process.

Chris saw possible alignment with **OpenID Federation**, particularly for trust across domains, and asked to review the slides in more detail. Gaowei agreed to circulate them and welcomed collaboration. This was an invitation to explore compatibility, not a decision to adopt a federation mechanism.

### VI. Trust establishment, security, and service credibility

Larry emphasized that interoperable communication and identity are not enough: agents also need a basis for trusting counterparties, tracking their activity, and responding when something goes wrong. He described work in the Agent Trust Protocol community on mandates, human authorization, and checks before, during, and after task execution. He framed that work as complementary to other protocols and offered to present it when ready.

Chris highlighted the difficulty of bootstrapping trust, including Trust on First Use (TOFU). Discovering metadata and cryptographic keys can support authentication, but it does not automatically establish a cross-domain community's trust relationships. He suggested separating the process of establishing a trustworthy environment from transactions conducted inside that environment, rather than treating initial contact as permission to trust a counterparty for everything.

Gaowei distinguished identity security from service credibility. Proving that a message reaches the intended agent and that the agent controls its identity is different from deciding whether that agent provides reliable or high-quality service. The latter may depend on experience and other evidence beyond the protocol. He welcomed concrete trust mechanisms that could be examined for integration with the existing work.

No single trust model was selected, and no claim was made that DID, CIMD, or OAuth alone solves reputation or service quality.
