## Discussion Topics

### I. Relationship Between the Protocol Draft and the Implementation

Isaac asked how the implementation shown during the meeting connects to the protocol draft. Sean said that the implementation follows the ANP 1.1 design and is intended as a concrete implementation of the protocol concepts.

Song noted that the implementation code was still hosted in the existing open-source community repository while the process of contributing or moving relevant material into the W3C CG repository was ongoing. He said the group expected that transition to continue soon.

The implementation and authentication example discussed in connection with the meeting are available here:

- Code reference: https://github.com/agent-network-protocol/anp
- Authentication example: https://github.com/agent-network-protocol/anp/blob/master/examples/python/did_wba_examples/e1_authenticate_and_verify.py

### II. DID as an Identifier Versus a Rich Agent Identity

Isaac asked whether a DID is issued by another party or self-generated, and whether it can represent more than an identifier. He argued that an agent's meaningful identity may also depend on past behavior, beliefs, lineage, and accumulated internal history.

Sean explained that the current DID-WBA approach is designed first to let a developer deploy and declare an agent identity quickly under a Web domain. The domain provides an initial administrative and operational context, while the agent can publish descriptive information about itself.

Sean distinguished this basic declaration mechanism from broader trust. He said trust information could be developed through verifiable credentials, signed statements from other parties, and discovery or reputation services that collect information about a DID's behavior and third-party comments. In this framing, the DID is a resolvable identity anchor rather than a complete representation of an agent's character, history, or trustworthiness.

### III. Authentication Flow and Token Questions

Chris said the implementation walkthrough made the overall connection flow easier to understand, but asked for more detail about the token used after initial authentication, including its structure, contents, exchange, and the responsibilities of the parties handling it.

The example supplied for the meeting demonstrates a complete DID-WBA authentication sequence: creating a DID document and authentication keys, signing an HTTP request, verifying the DID binding and request signature, issuing and caching a bearer access token, and authenticating a subsequent request with that token.

The group also treated authentication and trust as related but distinct concerns. A technically valid signature establishes control of the relevant key and supports request authentication, but does not by itself answer whether the remote agent should be trusted or authorized for a particular interaction.

### IV. Discovery Before Connection

Chris observed that the example connection flow begins with a remote agent URL. He asked how a client discovers that URL, decides among multiple agents offering a similar capability, and determines whether it should connect in the first place. He described this as both a discovery question and a precursor trust or negotiation step.

Sean clarified that the example was intended to show what happens after the caller already knows the remote agent URL. The “crawler” label referred to a client module and did not mean that the example itself discovered candidate agents. The current code walkthrough showed how to create an agent, connect to a known agent endpoint, authenticate, retrieve its description or interface information, and decide how to use its tools.

Sean described a broader discovery-service concept that could complement the example. An agent could register its DID and description with a directory or search service. The service could index the published material and, when queried in natural language or another structured form, return candidate DIDs, descriptions, and endpoints. He noted that this discovery service was not implemented in the specific example shown during the meeting.

Chris recommended making the boundary explicit in the documentation: either define discovery in scope or state clearly that the connection example begins after discovery. He also pointed to mature prior art from Wi-Fi networking, including IEEE 802.11u, Passpoint/Hotspot discovery, and ANQP pre-association queries, where a device can learn about network capabilities before deciding to associate.

Song summarized two possible documentation improvements:

- Rename the relevant example or section so that it does not imply that discovery is already performed by the URL-based connection flow.
- Give discovery its own extensible section, leaving room for future mechanisms and implementation work.

Sean agreed that the naming should be clarified and that local or proximity-based discovery ideas could be useful additions alongside the existing Web and directory-service concepts.

### V. Domain Requirements, DID Ownership, and Lifecycle

Ren Yushan asked whether every individual agent needs its own domain, how an agent identity can be associated with a person or company, whether one agent can have multiple DIDs, and what happens to the DID of a short-lived agent after the agent completes its task.

Sean said the current DID-WBA format publishes the DID document beneath a domain. An agent owner who does not operate a domain could use a hosted public service, in much the same way that a user can obtain an address from an email provider. This allows individual developers or users to publish DID documents without operating their own domain infrastructure.

For lifecycle management, Sean said that the current model treats the DID document as being published and managed by the agent or its operator and signed with the relevant private key. Creation, update, retention, and retirement are therefore primarily controlled by the identity owner or hosting arrangement. The questions of binding an agent to a person or organization, handling multiple DIDs for one agent, and defining retention expectations for ephemeral agents remain areas that would benefit from clearer policy and documentation.

### VI. Relay Messaging, Privacy, Auditing, and Cross-Domain Communication

Ren also asked whether two agents communicate directly or through a server. He noted that some use cases may require a server-mediated path for auditing, while privacy-sensitive interactions may prefer direct communication. He also asked how agents hosted under different domains communicate.

Sean explained that many user-controlled agents will not have a public IP address or publicly reachable service endpoint. The proposed implementation therefore supports a relay server that can receive and forward messages for such agents. The relay may be associated with the service hosting the agent's DID document.

Messages are intended to be encrypted end to end using agent-controlled key material. Under that model, the relay transports ciphertext but cannot read the message contents. Agents under different domains can communicate through their respective relay infrastructure, with the final recipient decrypting the message locally. Sean noted that the presentation did not include all implementation details of this end-to-end encrypted flow.

The discussion highlighted that relay transport, content confidentiality, and audit requirements should be documented separately. A relay can record transport events or delivery metadata, but end-to-end encryption limits its access to message content unless a use case explicitly introduces another audit mechanism.

### VII. Relationship to IETF Work and Authorization

George welcomed the end-to-end view but asked how the proposal relates to work underway in the IETF. He noted that multiple communities are addressing similar problems in discovery, agent protocols, identity, and authorization, even if they use different identity technologies. He also encouraged the group to examine mission-bound authorization and other work on restricting an agent's authority to its delegated task.

Song agreed that the CG should define its scope carefully, study relevant lower-layer IETF mechanisms, and avoid duplicating mature work. Reusing or building on established Internet protocols would reduce complexity and help the CG produce a more robust result.

Sean described the implementation's current kernel as DID-based identity, Web authentication and interoperability, agent capability description, and discovery. Messaging, human-readable naming, and related services can be treated as scenarios or layers built on that kernel and used to test whether the foundational protocol works in practice. He said the CG should decide which parts are appropriate for standardization.

George summarized the common semantic foundation as a **resolvable identifier that leads to metadata**. The resolution result can contain public keys, capabilities, service endpoints, and other information needed for discovery and interaction. He suggested that this is a natural starting point even when other ecosystems use resolution mechanisms other than DID.

### VIII. Closing and Future Demonstration

Song thanked participants for their questions and feedback and closed the meeting after it ran beyond the scheduled time. He said the minutes would be circulated by email and suggested that the group may include a short practical demonstration at the next meeting.
