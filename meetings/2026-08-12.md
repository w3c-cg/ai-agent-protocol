# Meeting Assets for AI Agent Protocol CG Meeting

**Date**: 2026-08-12

## Quick Recap

The W3C AI Agent Protocol Community Group meeting on August 12, 2026 focused on two related extensions to the group's identity work. First, participants reviewed the proposal to make the Agent Identity layer independent of any single DID method while retaining `did:wba` as a method defined by the protocol. The proposed update supports `did:wba`, native `did:web`, and `did:webvh` through a common authentication flow, with resolution and validation selected directly from the method name encoded in the DID. For `did:webvh`, this includes validation of its self-certifying identifier and verifiable update history. The group was invited to review and comment on the corresponding GitHub pull request.

Second, Sean presented an early architectural proposal, under a provisional open-verifiable-agent-interoperability name, for connecting agents that use different identity, authentication, and authorization technologies. The proposal separates identity, authentication, authorization, messaging, and service invocation so that DID-based agents could potentially interoperate with agents or workloads using OAuth client metadata, WIMSE-style workload identity, PKI, or similar cryptographically verifiable identity mechanisms. Common message and RPC interactions would sit above adapters for the underlying identity systems, while protected-resource access could reuse OAuth authorization infrastructure and RFC 9728 protected-resource metadata.

The discussion strongly supported the interoperability objective but identified substantial work still required. Professor Kim emphasized the need for concrete adapters and real-system validation between DID and OAuth-based ecosystems. Chris described the proposal as a promising blueprint or service-bus-like architecture, while asking the group to distinguish authentication and authorization from reciprocal trust evaluation and to clarify whether the intended output is a standard, a community best practice, an implementation framework, or some combination of these. Song called for milestones, prototypes, performance and complexity evaluation, and a careful assessment of robustness before the group commits significant resources. The meeting closed with an update about another W3C effort on agentic discovery and the possibility of inviting its participants to a future call.

## Discussion Topics

### I. Opening and Meeting Scope

Song opened the meeting by referring to the previous discussion about an open and verifiable interoperability model for agents, an idea originally prompted by George's comments. Sean and Gaowei had conducted follow-up study and concluded that the model could complement existing agent protocols, particularly where agents use different identity systems.

Song described two main objectives for the call:

- Review how the protocol could support native `did:web` and `did:webvh` in addition to `did:wba`.
- Hear Sean's initial architectural proposal for broader interoperability across identity, authentication, authorization, messaging, and service access.

### II. Common Support for Multiple DID Methods

Before the main presentation, Professor Kim asked whether the architecture would provide an adapter or common integration model for DID methods other than the Web-based method already used by the group, such as `did:webvh` or other DID variants.

Song said that the group's original design built on W3C DID and Web infrastructure, but that interoperability with other identity systems—including OAuth and OpenID-based systems—had always been an important goal. Sean summarized the desired DID architecture as a common interface through which different DID methods can be implemented and used within the same agent authentication environment.

Sean then introduced the protocol-document pull request prepared by Gaowei. The proposed document changes make the Agent Identity layer DID-method-agnostic while retaining the method-specific rules and guarantees of each supported method:

- **`did:wba`** continues to use the Web-based resolution, path binding, DID Document proof, and HTTP authentication rules defined by the protocol.
- **Native `did:web`** follows its own resolution rules and is not required to satisfy `did:wba`-specific path-binding or proof requirements.
- **`did:webvh`** follows its own resolution rules and requires validation of its self-certifying identifier and verifiable history before the resolved DID Document can be used for authentication.

The shared HTTP authentication layer resolves the DID according to the method encoded in the identifier, validates the applicable DID Document or history, checks that the key referenced by `keyid` is authorized by the DID Document's `authentication` relationship, and then verifies the HTTP Message Signature. A separate `identityType` field is unnecessary because the DID itself identifies its method.

Sean encouraged members to review the pull request and place detailed technical comments on GitHub so that the change can become a community-reviewed contribution.

### III. Motivation for a Broader Interoperability Model

Sean explained that the broader proposal arose from George's observation in the previous meeting that standardized OAuth client metadata has structural similarities to DID-based identity publication. Both approaches can associate a resolvable identifier or URL with a JSON metadata document containing an identifier, public-key information, and other information needed to recognize and authenticate an independent client.

This raised a broader question: rather than requiring every existing OAuth, workload, or PKI environment to migrate to DID, could the agent protocol recognize multiple cryptographically verifiable identity mechanisms behind a common interaction model?

Sean proposed separating the architecture into at least the following concerns:

1. **Identity**: how an agent or workload is identified and how its public verification material and claims are resolved.
2. **Authentication**: how an agent proves control of the corresponding private key or credential.
3. **Authorization**: how the authenticated agent obtains permission to use another agent's resources or services.
4. **Messaging**: how two authenticated agents exchange messages, including encrypted messages.
5. **Service invocation**: how one agent invokes an RPC, MCP, A2A, or other service exposed by another agent.

By separating these layers, a common message or RPC mechanism could potentially operate across agents using DID, OAuth client metadata, WIMSE-related workload identity, PKI, or another sufficiently verifiable mechanism. The intent is not to claim that all identity technologies are identical, but to define the common interface and security properties required for interoperation while preserving the distinct trust model of each technology.

### IV. Provisional Open Verifiable Agent Interoperability Model

Sean used a provisional name for the architecture based on the concepts of openness, verifiability, agents, and interoperability. He clarified that the name and acronym are not final. In the proposal:

- **Open** means that agents from different ecosystems and identity technologies can participate.
- **Verifiable** means that identity and authentication depend on cryptographic verification rather than unsupported self-assertion.
- **Agent interoperability** includes both message exchange and service or RPC invocation, with authorization applied where protected resources are involved.

The proposed architecture resembles a pluggable identity and authorization layer. An agent runtime or server could expose adapters for supported identity technologies. A calling-side adapter would discover the identity and authorization mechanism used by the remote system, while a receiving-side adapter would validate the caller and map its claims into the local security model.

Sean suggested starting with the multi-DID capability already being added to the protocol. Once the common adapter boundary is understood for `did:wba`, `did:web`, and `did:webvh`, the same architectural approach could be tested with selected non-DID identity mechanisms that offer similar key-bound and resolvable metadata properties.

### V. Interoperability with OAuth Client Metadata and Existing Systems

Sean emphasized that the proposal should not attempt to combine or replace the entire OAuth ecosystem. The first practical target would be narrower: support OAuth clients that publish standardized client metadata containing the identifiers and key material required for verification.

Two reciprocal scenarios were identified:

1. A DID-based agent needs to communicate with or access a service in an OAuth-based environment.
2. An agent represented through OAuth client metadata needs to communicate with or access a service offered by a DID-based agent.

If both sides can prove control of their respective key material and the receiving side has an adapter capable of validating that identity type, the agents could authenticate one another and then use a shared messaging or service-access flow. Sean described this as a progressive integration path that connects emerging DID-based agent networks with widely deployed OAuth infrastructure without requiring an immediate migration of existing systems.

The discussion also referenced workload-identity and PKI environments. Sean suggested that these may eventually participate where they provide comparable cryptographic identity and verifiable claims, but the scope should remain deliberately constrained rather than attempting to support every historical identity mechanism at once.

### VI. Common Messaging and End-to-End Encryption

Sean proposed a universal or common messaging layer above the identity adapters. After mutual authentication, agents using different identity systems could exchange messages through the same protocol, including an end-to-end encrypted channel when suitable key-agreement material is available.

The value of this approach is that message interoperability would no longer depend on both agents using the same identity mechanism. The identity adapter would establish who controls the relevant key and which claims or credentials are available; the messaging layer would then handle message protection and exchange independently of whether the identity originated from `did:wba`, another DID method, OAuth metadata, or a supported workload identity system.

Sean framed this as an extension of message and encryption capabilities already explored in ANP. The CG would need to determine which parts belong in the protocol specification and which should remain implementation guidance or an experimental testbed.

### VII. Protected Resources, RFC 9728, and UMA for Agents

Sean then discussed service invocation and protected-resource access. Message exchange alone is insufficient because agents also need to call APIs, RPC interfaces, MCP tools, A2A services, and other protected endpoints.

The presentation referenced RFC 9728, OAuth 2.0 Protected Resource Metadata. Under this pattern, when a client attempts to access a protected resource, the resource server publishes metadata that identifies the appropriate authorization server and other authorization information. The client can then authenticate to that authorization server, obtain an access token, and retry access to the protected resource.

Sean connected this flow to UMA-for-agent ideas. An agent could declare authorization information for the resources and services it controls. A caller would:

1. Discover or request the protected resource.
2. Obtain its authorization metadata.
3. Locate the designated authorization server.
4. Authenticate using a supported identity adapter.
5. Obtain an access token or equivalent authorization result.
6. Use the token to access the resource or invoke the service.

For this to support heterogeneous agents, the authorization server would need to validate more than one agent identity technology. Instead of modifying every MCP, RPC, or A2A service individually, deployments could add supported identity adapters at the authorization layer and continue using a common protected-resource authorization flow.

Sean stressed that this proposal does not redefine MCP or A2A. Those protocols can remain service or interaction mechanisms. The proposed work focuses on the identity, authentication, and authorization bridge needed when the calling and receiving agents belong to different identity ecosystems.

### VIII. Development Plan and Need for Concrete Outputs

Song asked whether ANP or the relevant open-source community had a development plan, timetable, specification plan, or demonstration target for the proposed architecture. He asked whether the work was intended for the next two or three months or as a longer-term direction for the following year.

Sean said that the immediate multiple-DID work provides a practical starting point. A common adapter could first be implemented for several DID methods and then extended experimentally to another identity technology, such as the relevant OAuth metadata approach. Existing open-source authorization projects could also be integrated into a demonstration so that the group can observe a complete identity, authentication, token, messaging, and resource-access flow.

No fixed timetable was agreed. Song emphasized that a promising architecture still requires concrete outputs before the group commits substantial resources. These outputs should include:

- A clearer architectural definition and scope.
- One or more protocol or adapter prototypes.
- End-to-end demonstrations across different identity ecosystems.
- Measurements or analysis of performance, implementation complexity, and operational overhead.
- Security and robustness evaluation.
- Milestones that allow the group to decide whether and how to advance the work.

### IX. Professor Kim's Interoperability Questions

Professor Kim summarized the proposal as a unified platform for handling multiple identity and authorization mechanisms and enabling mutual authentication between them. He supported the objective, especially for scenarios in which one agent ecosystem uses DID while another uses OAuth-based identity.

He cautioned, however, that the group needs much more discussion about how to realize the architecture in an actual system. A conceptual adapter is not sufficient by itself; the group needs to define the translation boundaries, trust assumptions, credential mappings, authentication procedures, and authorization behavior needed for practical interoperability.

Sean agreed that substantial design and implementation work remains. Song connected this concern to his question about timelines and milestones, saying that feasibility, complexity, performance, and robustness must be tested through prototypes rather than assumed from the high-level model.

### X. Chris Phillips's Blueprint, Trust, and Standardization Feedback

Chris said the architecture describes a real problem faced by anyone implementing a multi-protocol agent environment. Today, a developer combining MCP, A2A, DID, OAuth, OpenID Connect, SAML, or federation technologies often has to assemble the identity and authorization mappings manually.

He characterized the current proposal as a strong **blueprint**, with similarities to a service bus into which different authentication, authorization, and trust mechanisms can be plugged. He asked the group to clarify where the work belongs on the spectrum between:

- A normative standard.
- A community best practice.
- An architectural blueprint.
- A reusable implementation framework.

Chris also distinguished authentication and authorization from trust. Successful authentication proves control of an identity or credential, and authorization may grant access, but neither necessarily means that the remote party is trustworthy. An agent could successfully authenticate to a malicious actor. The architecture therefore needs an explicit or better-defined trust-evaluation component, including reciprocal evaluation of the party and context before interaction.

Another challenge is semantic equivalence across ecosystems. An identifier or claim used in DID may not map directly to a SAML subject, OpenID Connect claim, MCP authorization context, A2A identity, or token-exchange result. A useful specification should make these translations clearer, expose their security characteristics, and show implementers where equivalence cannot safely be assumed.

Chris said the opportunity is significant because agent identity remains fragmented across multiple emerging protocols. A shared architecture could reduce uncertainty, make complex integration easier, and expose risks that are currently hidden in custom implementations. He offered to continue discussing the architecture with Sean outside the group call.

Sean responded that the initial scope should remain narrow. The proposal does not attempt to bridge every SAML, OAuth, MCP, or A2A deployment. It would begin with identity representations that resemble the DID model by providing a resolvable identifier, cryptographic key material, and verifiable metadata. It would then address two concrete interactions: cross-identity messaging and cross-identity access to protected services.

### XI. Scope and Emerging Consensus

The discussion produced broad support for the interoperability goal but not yet for a final architecture or standardization plan. The emerging direction can be summarized as follows:

- Start with method-agnostic support across multiple DID methods.
- Derive the DID method directly from the DID rather than adding redundant type metadata.
- Preserve method-specific verification and trust properties rather than flattening all methods into one security model.
- Define a narrow adapter interface around resolvable, cryptographically verifiable identities.
- Separate identity, authentication, authorization, trust evaluation, messaging, and service invocation.
- Test both cross-identity message exchange and cross-identity protected-resource access.
- Reuse existing standards such as OAuth protected-resource metadata rather than redefining service authorization.
- Determine through implementation whether the result should become a standard, best-practice document, blueprint, or reusable framework.

No decision was made to expand the current CG specification immediately to cover all non-DID identity technologies. The wider interoperability model remains an early proposal requiring further refinement and evidence.
